# Energy Certificate Authority

## Overview

The Energy Certificate Authority (ECA) is a smart-contract based system that issues verifiable, tamper-proof certificates for renewable energy generation. Each certificate attests that a specific quantity of renewable energy was generated by a specific producer during a specific period, and carries a cryptographic proof of authenticity that any third party can independently verify.

The system is designed to satisfy the following goals:

- **Issue certificates for verified generation** — certificates are minted only after generation data has been verified.
- **Third-party verification integration** — external verifiers (auditors, registries, oracles) can attest to generation data before issuance.
- **Cryptographic proof of authenticity** — every certificate commits to a hash digest of its underlying data and is signed by the issuing authority.
- **Revocation mechanism** — fraudulent or erroneous certificates can be revoked and are permanently marked as invalid.
- **International standard compliance** — the data model and lifecycle align with common renewable energy certificate standards (e.g. I-REC, Guarantees of Origin under the EU RED II, and RECs).
- **Lifecycle tests** — the full lifecycle (issue → verify → transfer/retire → revoke) is covered by tests.

## Core Concepts

| Concept | Description |
| --- | --- |
| **Producer** | The registered renewable energy generator that owns the generation asset. |
| **Verifier** | An authorized third party that attests to generation data. |
| **Certificate** | An on-chain record attesting to a quantity of renewable energy generation. |
| **Proof Digest** | A cryptographic hash committing to the certificate's underlying data. |
| **Status** | The lifecycle state of a certificate: `Issued`, `Retired`, or `Revoked`. |

## Certificate Data Model

Each certificate stores the following fields:

```
struct EnergyCertificate {
    uint256 id;              // Unique certificate identifier
    address producer;        // Registered producer / owner
    address verifier;        // Third party that verified the generation
    uint256 energyAmount;    // Amount of energy in watt-hours (Wh)
    uint256 generationStart; // Unix timestamp of generation period start
    uint256 generationEnd;   // Unix timestamp of generation period end
    bytes32 energySource;    // Source type (solar, wind, hydro, ...)
    bytes32 region;          // Geographic / market region code
    bytes32 proofDigest;     // Hash committing to the underlying generation data
    Status  status;          // Issued | Retired | Revoked
    uint256 issuedAt;        // Timestamp of issuance
}
```

The `proofDigest` is computed off-chain over a canonical serialization of the generation data (see [Cryptographic Proofs](#cryptographic-proofs)) and is stored on-chain so that the certificate can never be silently altered.

## Issuance

### Prerequisites

1. The producer must be registered and active.
2. The verifier must be an authorized verifier for the relevant region/source.
3. The generation period must not overlap with an already-issued certificate for the same producer and asset (prevents double counting).

### Issuance Flow

1. **Submit generation data** — the producer (or an oracle) submits the generation record: amount, period, source, region, and the `proofDigest`.
2. **Verification** — an authorized verifier attests to the record by submitting a verification signature/transaction. The contract records the verifier address on the certificate.
3. **Minting** — once verified, the contract mints a certificate with a unique `id`, sets `status = Issued`, and records `issuedAt`.
4. **Event emission** — a `CertificateIssued` event is emitted containing the certificate id, producer, verifier, amount, and `proofDigest`.

### Issuance Rules

- A certificate can only be issued for a **positive** energy amount.
- `generationEnd` must be greater than `generationStart`.
- Only authorized verifiers may trigger the verification step.
- Each `(producer, generationStart, generationEnd)` tuple may produce at most one certificate.

## Third-Party Verification

Third-party verification is the mechanism by which external trust is injected into the system. The contract supports a registry of authorized verifiers.

### Verifier Registry

- The contract owner (or governance) can `addVerifier` and `removeVerifier`.
- Each verifier has an associated scope (region and/or energy source) it is authorized to verify.
- Only verifiers whose scope matches the certificate's `region` and `energySource` can attest to it.

### Verification Protocol

1. The verifier independently validates the generation data against metering records, grid data, or other evidence.
2. The verifier computes the `proofDigest` using the canonical hashing scheme and compares it to the digest submitted by the producer.
3. The verifier calls `verifyGeneration(certificateId, proofDigest)` (or signs an off-chain attestation that is relayed on-chain).
4. The contract checks that the verifier is authorized, that the digest matches, and that the certificate is not already verified.
5. On success, the certificate transitions to `Issued` and the verifier address is recorded.

### Verification Events

- `VerifierAdded(address verifier, bytes32 region, bytes32 source)`
- `VerifierRemoved(address verifier)`
- `GenerationVerified(uint256 certificateId, address verifier, bytes32 proofDigest)`

## Cryptographic Proofs

Certificates are tamper-proof because every certificate commits to a cryptographic digest of its underlying data, and the digest is anchored on-chain.

### Canonical Serialization

The generation data is serialized in a deterministic order:

```
producer || energyAmount || generationStart || generationEnd || energySource || region || meterReading
```

Each field is encoded in a fixed-width, big-endian representation to avoid ambiguity.

### Digest Computation

```
proofDigest = keccak256(canonicalSerialization)
```

The digest is stored in the certificate. Any party can recompute the digest from the original generation data and compare it to the on-chain value to confirm the certificate has not been tampered with.

### Authority Signature

In addition to the digest, the issuing authority signs the certificate id and digest:

```
signature = sign(authorityPrivateKey, keccak256(certificateId || proofDigest))
```

Consumers of the certificate can verify the signature against the published authority public key, providing an independent proof of authenticity that does not rely solely on the contract state.

### Tamper-Proof Records

- Certificate fields are immutable after issuance (except `status` for retirement/revocation).
- The `proofDigest` cannot be changed after issuance.
- All state transitions emit events, producing an auditable, append-only log.

## Revocation

Fraudulent or erroneous certificates must be revocable.

### Revocation Flow

1. An authorized party (contract owner, governance, or the original verifier) calls `revokeCertificate(certificateId, reason)`.
2. The contract checks that the certificate exists and is not already revoked.
3. The certificate's `status` is set to `Revoked`.
4. A `CertificateRevoked` event is emitted with the certificate id, revoking party, and reason.

### Revocation Rules

- A `Revoked` certificate can never be re-issued or re-activated.
- Revoked certificates are excluded from all valid-certificate queries and cannot be retired or transferred.
- Revocation is permanent and recorded on-chain for auditability.

### Revocation Events

- `CertificateRevoked(uint256 certificateId, address revokedBy, bytes32 reason)`

## International Standard Compliance

The data model and lifecycle are designed to align with widely used renewable energy certificate standards:

- **I-REC (International REC Standard)** — supports issuance per MWh of generation, unique serial numbers, and a retirement mechanism.
- **Guarantees of Origin (EU RED II)** — tracks energy source, generation period, and issuing body, and supports cancellation/revocation.
- **RECs (North American Renewable Energy Certificates)** — supports tracking of generation attributes and retirement.

### Compliance Mapping

| Standard Requirement | Implementation |
| --- | --- |
| Unique serial number | `id` field, unique per certificate |
| Energy quantity (MWh) | `energyAmount` (stored in Wh, convertible to MWh) |
| Energy source | `energySource` |
| Generation period | `generationStart`, `generationEnd` |
| Issuing body | Authority signature + `verifier` field |
| Retirement / cancellation | `status = Retired` |
| Revocation | `status = Revoked` |
| Audit trail | Event log |

## Lifecycle

A certificate moves through the following states:

```
        issue
          │
          ▼
      ┌────────┐   retire    ┌─────────┐
      │ Issued │────────────▶│ Retired │
      └────────┘             └─────────┘
          │
          │ revoke
          ▼
      ┌─────────┐
      │ Revoked │
      └─────────┘
```

- **Issued** — the certificate is valid and can be transferred or retired.
- **Retired** — the certificate has been consumed (e.g. to offset consumption) and can no longer be transferred.
- **Revoked** — the certificate has been invalidated due to fraud or error.

## Lifecycle Tests

The test suite covers the full certificate lifecycle. Key test cases include:

### Issuance Tests
- Issuing a certificate for a verified generation record succeeds and emits `CertificateIssued`.
- Issuing with a zero or negative energy amount reverts.
- Issuing with `generationEnd <= generationStart` reverts.
- Issuing a duplicate certificate for the same `(producer, period)` reverts.

### Verification Tests
- An authorized verifier can verify a pending generation record.
- An unauthorized verifier cannot verify a record.
- A verifier with a mismatched scope cannot verify a record.
- A mismatched `proofDigest` causes verification to revert.

### Cryptographic Proof Tests
- Recomputing the digest from the original data matches the on-chain `proofDigest`.
- Tampering with any field changes the digest and fails verification.
- The authority signature verifies against the published public key.

### Revocation Tests
- An authorized party can revoke an issued certificate.
- A revoked certificate cannot be retired or transferred.
- A revoked certificate cannot be re-issued.
- Revoking an already-revoked certificate reverts.
- `CertificateRevoked` is emitted with the correct reason.

### Retirement Tests
- An issued certificate can be retired.
- A retired certificate cannot be transferred.
- Retiring an already-retired certificate reverts.

### Compliance Tests
- Certificate fields map correctly to standard-required attributes.
- Event log provides a complete audit trail for each certificate.

## Security Considerations

- **Double counting prevention** — the `(producer, generationStart, generationEnd)` uniqueness constraint prevents the same generation from being certified twice.
- **Verifier authorization** — only scoped, authorized verifiers can attest to generation.
- **Immutability** — certificate data cannot be altered after issuance; only `status` transitions are permitted.
- **Auditability** — every state transition emits an event, producing a complete on-chain audit trail.
- **Cryptographic anchoring** — the `proofDigest` and authority signature provide independent, off-chain-verifiable proof of authenticity.
